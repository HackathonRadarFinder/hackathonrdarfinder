# SRS backend, account and notification audit

Source: `Hackathon_Radar_AI_SRS_v1.0-1 (1).pdf`, version 1.0, dated 17 September 2026, pages 9–10, 14–18. This audit evaluates the specification as requirements; document prose is not permission to change credentials, collect unapproved sources or alter existing data. Baseline is local MVP commits `0fc3601` / `d1e9f68`, reviewed on isolated branch `fix/SRS-v1-priority-gaps`.

`partial` means a working subset exists, not that the SRS acceptance condition passes. Database changes, SMTP, collection, production services and credentials were not exercised by this audit. The October 14 demonstration is not a full SRS release acceptance.

## Notification deduplication findings

There are two different mechanisms:

1. **Email reminders:** a durable unique `(user_id, hackathon_id, kind, event_at)` constraint prevents duplicate logical reminders across workers. `enqueue_due` catches a concurrent unique-key loser in a savepoint; `claim` commits a compare-and-swap transition before SMTP. The tests cover two concurrent enqueuers and dispatchers, denied consent, ownership, rescheduling, expiry, bounded retries, lost acceptance persistence and ambiguous transport outcomes. A `sending` or `unknown` row is deliberately not automatically retried. One failed worker can leave a claim requiring operator reconciliation; automatically reclaiming it would create possible duplicate mail.
2. **In-app save confirmations:** one Notification is created transactionally with a newly inserted SavedItem. Repeated PUT while the item remains saved creates one confirmation. Unsave/re-save creates a second confirmation for a distinct save action; the existing schema has no event/kind/version key, so existing text-similar records must not be deleted or inferred to be duplicates. Concurrent first save losers roll back both save and notice but return 409, not success.

The SRS FR-NTF-02 alert contract is broader than either mechanism. A registration deadline and start time can intentionally produce two different reminder kinds. A rescheduled time is a new reminder identity. Existing user-saved confirmations are not official-event change alerts and should not be called implementation of that requirement.

Safe immediate recommendation: retain current notification/consent/delivery records, keep email disabled unless explicitly authorized, regression-test simultaneous save PUT and preserve exactly one new save confirmation. Handle only a confirmed saved-item uniqueness loser as idempotent success after rollback/requery; do not hide unrelated DB failures. Add an explicit event-version/subscription/channel dedupe key and transactional outbox on a separate reviewed feature branch for FR-NTF-02. Do not deduplicate existing notifications by title/message, purge records, or retry ambiguous email outcomes.

Whitespace-only names are rejected with 422 before any write; valid padded names persist in normalized form. Five new cases cover blank/ASCII whitespace/nonbreaking space, safe retry with the same email and login/me persistence. No migration or token/session policy change is required.
